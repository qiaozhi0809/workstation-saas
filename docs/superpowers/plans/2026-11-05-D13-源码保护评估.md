# D13 源码保护评估(Nuitka 试编译)

> M5a Task 8 · 2026-11-05 · 段 D。所有数字为本机实测;未测的写"未测"并列入已知缺口。脚本在 [`deploy/experiments/nuitka/`](../../../deploy/experiments/nuitka/README.md)。

## 结论

**D13:已评估,v1 交付镜像不编译;构建开关 `WS_BUILD_NUITKA` 默认关。**(用户 2026-11-05 决定。)

评估事实:Nuitka 能编译本后端并通过冒烟,接口延迟无可测差异,启动快约 1–1.6 s(但对照组没有预编译字节码,见 ③);代价是镜像磁盘占用 +207 MB(`docker save` 压缩后 +56.5 MB)、冷构建约 30 分钟、产物绑定 CPU 架构,而保护强度有限(字符串、SQL、迁移脚本仍是明文)。

| 项 | 值 |

## ① 能否编译成功

能。**首次完整构建一次通过**(无编译期错误),运行期暴露 1 个问题,改一处参数后解决;另有若干 Nuitka 警告。

手工指定的 `--include-*`(全部写在 `nuitka.Dockerfile`;**未逐项消融**,不能断言每一项都是必需):

| 选项 | 目的 | 实测 |
|---|---|---|
| `--include-package=app` | 编译业务包 | 已包含(未单独验证必要性) |
| `--include-package=uvicorn` / `alembic` / `psycopg` / `structlog` / `sqlalchemy.dialects.postgresql` | 按名字动态加载的模块(uvicorn 的 loop/protocol、SQLAlchemy 方言、psycopg 实现) | 已包含,未单独验证必要性 |
| `--include-package=tzdata` + `--include-package-data=tzdata` | 学校时区(`ZoneInfo`) | 构建产生大量 `Duplicate data file tzdata/zoneinfo/*` 警告(被忽略,无害),说明二者重叠,其一可去 |
| `--include-raw-dir=migrations=migrations` | alembic 的 `env.py` 与 revision `.py` | **运行期错误**:先用 `--include-data-dir`,Nuitka 数据目录默认不拷贝 `.py`,`alembic upgrade` 报 `Can't find Python file /srv/dist/migrations/env.py`;改 `--include-raw-dir` 后通过 |
| `--include-data-files=app/seed/dev_seed.sql=…` | `app.cli.seed_dev` 读取 `Path(__file__).parent/"seed"`(编译后 `__file__` 仍指向 dist 内路径) | 通过 |
| 入口里 `import app.cli` | `app.cli` 不在 `app.main` 的导入链上,不显式导入就不会被编译 | 通过 |

pydantic:**没有手工 include**,冒烟与 pytest 子集均通过(`pydantic_core` 由 Nuitka 自动带入 dist)。SQLAlchemy 方言只手工加了 `sqlalchemy.dialects.postgresql`;`structlog` 同样已手工加入,未测不加会怎样。

警告:`older than the latest stable release '4.3.4'`(预期);`anti-bloat: Undesirable import of 'sqlalchemy.testing'`(来自 `sqlalchemy.dialects.postgresql.provision`,由本试验自己加的 `--include-package=sqlalchemy.dialects.postgresql` 引入;Nuitka 称"可能拖慢编译",对冷编译时间与体积的影响未测);anti-bloat 说不自动包含 `_json`、`_bisect`,"可能退回较慢实现"(未测其影响)。

**启动时间的归因要谨慎**:对照组镜像设了 `PYTHONDONTWRITEBYTECODE=1`,依赖装好后没有预编译字节码,基础镜像也不带标准库 `.pyc`,每次启动都要重新编译字节码(段 B 的生产镜像同样如此,所以对照组贴近生产)。1–1.6 s 的差距很可能主要来自这里,用 `UV_COMPILE_BYTECODE=1` 之类的做法源码版也能拿到,**不应算作 Nuitka 独有的收益**(未测加字节码后的启动时间)。编译版最终镜像以 `python:3.12-slim` 为底,standalone 产物用不到其中的 CPython 层(约 43.7 MB,`docker history` 估计值),所以 +207 MB 里包含这部分冗余(换底后的实际大小未测)。登录耗时主要来自 bcrypt(cost 10),编译不改变它,所以登录延迟几乎不变。

## ④ 保护强度

在编译版镜像里对 `/srv/dist` 检查:

- **没有 `app` 的 `.py` / `.pyc`**(`pyc` 0 个;`app/` 下只有种子 SQL)。传统的 `uncompyle6` / `pycdc` 类字节码反编译不适用。业务逻辑变成机器码(`ws-app` 136 MB + 70 个 `.so`)。
- **字符串全部可见**:在 `ws-app` 里直接检索到 `登录名或密码不正确`、`登录失败次数过多`、`INVALID_CREDENTIALS`、`ACCOUNT_LOCKED`、`_DUMMY_HASH`、`verify_password`、`issue_access_token`、`login_max_failures`、`parent_links`、模块名 `app.auth.service`、源文件相对路径 `app/auth/service.py`、`ws:refresh:` 这类 Redis 键前缀、631 处 `SELECT`。函数名、常量、SQL、错误码、接口文案都是明文,行为很容易靠阅读这些字符串推测。
- **迁移脚本完全明文**:`migrations/` 里 11 个 `.py` 和 20 个 `.sql` 原样在镜像里(`CREATE EXTENSION…` 等),数据库结构和约束一览无余。
- 未测:对机器码做反汇编/反编译(Ghidra 等)还原控制流的难度(D-5)。

结论:能挡住"解开镜像直接读 Python 源码"这一类最低成本的获取;挡不住读字符串与 SQL,也挡不住有逆向能力的人。没有机密(密钥)靠它保护的理由。

## ⑤ 对升级流程的影响

- **每个版本都要重新编译**:冷构建 ≈ 30 分钟(整次构建 1799 s,本机,2 并行),热缓存 ≈ 3 分钟;CI 的 `deploy` job 还没有 ccache 持久化,没算。
- **产物绑定 CPU 架构**:本次产物是 aarch64,交付目标 Ubuntu x86_64 必须在 x86_64 上重编,不能跨架构复用(D-2)。
- **入口不同**:编译版入口是 `ws-app`(`run_app.py` 的 `serve`/`migrate`/`seed`),**没有 `python -m app.cli …`**;段 A 的 `migrate`、`init-school`、`scheduler`、`diagnose`,以及 `upgrade.sh` 里调用的命令都基于 `python -m app.cli`,启用编译就要为它们逐个做编译版入口(D-7)。
- **迁移预检(`app/deploy/precheck.py`)**:本分支基于的 main 里还没有 `server/app/deploy/`(段 A 未合并),**编译后能否正常运行未测**(D-8)。编译后栈追踪没有源码行内容(`File "/srv/dist/run_app.py", line 32, in main` 只有行号),诊断包里的报错更难读。
- **与生产形态的差异(均未测)**:生产入口是 `uvicorn --factory app.main:create_app --workers 2`(多进程),试验入口是单进程 `uvicorn.run(create_app())`,Nuitka 下多 worker 子进程能否启动未测;试验镜像以 root 运行,生产是 uid 10001 非 root 用户;生产 `HEALTHCHECK` 用 `python -c`,编译版若换不带 Python 的底镜像,健康检查需要改(D-9)。
- **离线包体积**:`docker save` 实测从 71.8 MB 增到 128.3 MB(+56.5 MB,压缩层;离线包若再整体压缩,未测)。

## ⑥ 结论与建议

- v1:**不编译**(见顶部结论)。`app.Dockerfile` 的 `ARG WS_BUILD_NUITKA=0` 开关保留,默认关;本段未改 `deploy/docker/**`,开关的具体写法能否承载本试验用的这组选项,待段 B 合并后核对(D-4)。
- v2 若要启用,前置条件:① 在 x86_64 上复测构建、体积与冒烟(D-2);② 在 `--standalone` 产物上直接跑后端冒烟子集(D-3);③ 为所有运维命令提供编译版入口(D-7);④ 明确威胁模型——若目标是保护"迁移 SQL / 文案 / 接口名",编译不够,需要另外设计(如迁移脚本打包校验);⑤ CI 持久化 ccache,否则每次发布冷编译约半小时;⑥ 逐项消融 `--include-*` 清单并锁定(D-5)。

## 偏差

1. 计划写 `--include-data-dir=migrations=migrations`:实测不行(不拷 `.py`),改为 `--include-raw-dir`。
2. 计划只写 `--standalone` 编译 + 试验镜像;为在不含 `app` 源码的环境里跑 pytest,额外增加 `--module` 构建阶段(`pytest-compiled`)。
3. 计划标 `build.sh` 一个文件;实际还有 `nuitka.Dockerfile`、`nuitka.Dockerfile.dockerignore`、`run_app.py`、`smoke.sh`、`smoke.compose.yml`、`bench.py`,均在 `deploy/experiments/nuitka/` 内。
4. 同时构建源码对照镜像 `workstation-app-baseline:0.0.0-seg-d`(为了公平对比),段结束时与其他镜像一并删除。
